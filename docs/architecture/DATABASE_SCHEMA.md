# Foundation Database Schema

**Scope:** Version 0.1 foundation tables only
**Status:** Proposed baseline for Product Owner and Technical Lead review
**Database:** PostgreSQL managed by Supabase
**Related:** [ERD](ERD.md), [Permissions](PERMISSIONS.md)

## 1. Conventions

- Use UUID primary keys generated by PostgreSQL for application-owned rows.
- Store timestamps as `timestamptz` in UTC. Use the school's IANA timezone for display and school-local calendar rules.
- Use `created_at` and `updated_at` on mutable entities. Sensitive writes also record the actor in the audit log.
- Store account credentials only in Supabase Auth. Do not duplicate passwords, recovery tokens, or service-role credentials in application tables.
- Use stable text codes for roles, permissions, statuses, and audit actions; validate them with checks or seeded reference rows.
- Add `school_id` to every school-owned table and use same-school composite constraints where relationships cross school-owned records.
- Prefer deactivation/status changes over deleting users or students. Retention/anonymization policy must be approved before pilot data is used.

## 2. Tables

### `schools`

| Column | Type | Constraints / purpose |
| --- | --- | --- |
| `id` | `uuid` | Primary key |
| `name` | `text` | Required, non-empty |
| `default_locale` | `text` | Required; `ar` or `en`, default `ar` |
| `timezone` | `text` | Required IANA timezone identifier |
| `status` | `text` | Required; `active` or `inactive` |
| `created_at`, `updated_at` | `timestamptz` | Required; UTC |

### `profiles`

One row per authenticated Supabase Auth identity. Profiles exist only for people who can sign in; student educational profiles do not depend on this table.

| Column | Type | Constraints / purpose |
| --- | --- | --- |
| `id` | `uuid` | Primary key and foreign key to `auth.users(id)`; do not cascade-delete educational history |
| `display_name` | `text` | Required, non-empty |
| `preferred_locale` | `text` | Required; `ar` or `en`, default `ar` |
| `status` | `text` | Required; `active`, `inactive`, or `suspended` |
| `created_at`, `updated_at` | `timestamptz` | Required; UTC |

The profile is not an authorization source by itself. School access comes from an active school membership and role permissions.

### `school_memberships`

| Column | Type | Constraints / purpose |
| --- | --- | --- |
| `id` | `uuid` | Primary key |
| `school_id` | `uuid` | Required foreign key to `schools(id)` |
| `profile_id` | `uuid` | Required foreign key to `profiles(id)` |
| `status` | `text` | Required; `invited`, `active`, `suspended`, or `ended` |
| `created_at`, `updated_at` | `timestamptz` | Required; UTC |

Constraints: unique `(school_id, profile_id)`; also expose a unique `(school_id, id)` key for tenant-safe composite references.

### `roles`, `permissions`, and `role_permissions`

`roles` contains stable role definitions such as `administrator`, `teacher`, and `student`. `permissions` contains stable action codes such as `school.people.manage` and `audit.read`. Both have UUID primary keys, unique non-empty `code`, and a display `name`.

`role_permissions` joins roles to permissions with foreign keys and a unique `(role_id, permission_id)` constraint. Seed changes are delivered as reviewed, idempotent migrations. Do not let mobile clients grant roles or permissions.

### `membership_roles`

| Column | Type | Constraints / purpose |
| --- | --- | --- |
| `membership_id` | `uuid` | Required foreign key to `school_memberships(id)` |
| `role_id` | `uuid` | Required foreign key to `roles(id)` |

Use `(membership_id, role_id)` as the primary key. A user can hold multiple roles in a school without duplicating the account.

### `teachers`

| Column | Type | Constraints / purpose |
| --- | --- | --- |
| `id` | `uuid` | Primary key |
| `school_id` | `uuid` | Required foreign key to `schools(id)` |
| `profile_id` | `uuid` | Required authenticated profile; unique within the school |
| `teacher_code` | `text` | Optional school-scoped identifier |
| `status` | `text` | Required; `active` or `inactive` |
| `created_at`, `updated_at` | `timestamptz` | Required; UTC |

Require `(school_id, profile_id)` to reference a membership in the same school. If `teacher_code` is present, enforce uniqueness within that school.

### `students`

This is the educational student record. It may exist without any Supabase Auth user, email, phone number, or `profiles` row.

| Column | Type | Constraints / purpose |
| --- | --- | --- |
| `id` | `uuid` | Primary key |
| `school_id` | `uuid` | Required foreign key to `schools(id)` |
| `profile_id` | `uuid` | Nullable; optional linked login profile, unique within the school when present |
| `display_name` | `text` | Required, non-empty |
| `student_code` | `text` | Optional school-scoped identifier |
| `date_of_birth` | `date` | Optional; collect only if the school has an approved need |
| `level` | `text` | Optional school-defined level |
| `status` | `text` | Required; `active`, `inactive`, or `withdrawn` |
| `created_at`, `updated_at` | `timestamptz` | Required; UTC |

Require `(school_id, profile_id)` to reference a membership in the same school when `profile_id` is non-null. A linked profile receives the student role for that membership. Enforce uniqueness for a non-null `student_code` within a school. Do not store an account password or fabricate a recovery email in this table.

### `audit_logs`

Append-only records for sensitive foundation events.

| Column | Type | Constraints / purpose |
| --- | --- | --- |
| `id` | `uuid` | Primary key |
| `school_id` | `uuid` | Nullable only for approved platform/bootstrap events; otherwise references `schools(id)` |
| `actor_profile_id` | `uuid` | Nullable for system/bootstrap events; references `profiles(id)` when present |
| `action` | `text` | Required stable event code |
| `resource_type` | `text` | Required resource category |
| `resource_id` | `uuid` | Resource identifier; not a polymorphic foreign key |
| `request_id` | `uuid` | Request/correlation identifier |
| `metadata` | `jsonb` | Redacted, allow-listed event details only |
| `created_at` | `timestamptz` | Required; UTC |

Never include passwords, access/refresh tokens, recovery tokens, full authentication payloads, or unnecessary child-sensitive data in audit metadata. Updates/deletes are denied to application roles.

## 3. Relationship and Integrity Rules

- `profiles.id` maps one-to-one to `auth.users.id`.
- A profile may have memberships in multiple schools; each school/profile pair is unique.
- A membership may have multiple roles; the same role is not duplicated on one membership.
- A teacher row must reference an active or inactive membership for the same school and carry the teacher role while active.
- A student row belongs to exactly one school. Its `profile_id` is optional; if present, it must reference a membership in that same school and carry the student role while active.
- Role changes and deactivation must not erase lesson or audit history added by later migrations.
- Use database checks for non-empty names/codes, valid status values, and allowed locale values.
- Apply RLS to every exposed school-owned table. The schema constraints prevent invalid relationships; RLS enforces who can access valid rows.

## 4. Indexes

Create indexes with the initial migrations for known access paths:

- `school_memberships(school_id, status)` and `school_memberships(profile_id, status)`.
- `membership_roles(membership_id, role_id)`; the primary key covers this lookup.
- `teachers(school_id, status)` and a unique partial index on `(school_id, teacher_code)` when the code is not null.
- `students(school_id, status)` and a unique partial index on `(school_id, student_code)` when the code is not null.
- Unique indexes on `(school_id, profile_id)` for teachers and on the non-null student account link.
- `audit_logs(school_id, created_at DESC)` and `audit_logs(actor_profile_id, created_at DESC)`.
- Foreign-key columns used by joins and delete/update checks.

Review query plans against representative data before adding speculative indexes. Avoid indexing sensitive fields without a defined query need.

## 5. Migration and Seed Order

1. Create shared extensions/functions required by the schema, using the platform's supported Supabase migration conventions.
2. Create schools, profiles, memberships, roles, permissions, role grants, teachers, students, and audit logs.
3. Add checks, unique constraints, tenant-safe foreign keys, and indexes.
4. Seed stable role/permission definitions idempotently.
5. Enable RLS and add table-specific policies; grant no broad client access by default.
6. Add controlled bootstrap and profile/membership provisioning logic with tests; do not expose a public first-admin endpoint.

Every schema change is a versioned SQL migration. Verify applying all migrations and seeds to an empty local database, and verify upgrade migrations from the immediately preceding schema. Production migrations run through a controlled deployment pipeline with backup/rollback procedures; do not edit production data/schema manually to complete setup.

## 6. Deferred Tables

Do not create unused placeholders in 0.1. Add tables through later migrations when their version begins: academic terms/groups in 0.2; Qur'an reference metadata/homework/assessments in 0.3; reader-specific cache/bookmarks as needed in 0.4; attendance/revision in 0.5; scoring ledger/competitions in 0.6; notifications/outbox in 0.7; analytics projections in 0.8; local mutation idempotency/sync support in 0.9.

## 7. Review Gate

Before 0.1 implementation, Product Owner and Technical Lead approve optional student account linking, membership/role representation, audit retention, and bootstrap behavior. The Technical Lead verifies composite foreign-key feasibility with Supabase/PostgreSQL migrations and validates all RLS policies using the permission test matrix.

## 8. Target-Domain Schema Catalog

This section defines the planned logical schema beyond 0.1 so relationships and invariants are designed before feature growth. It does **not** authorize creating unused tables early. Add each entity only in the milestone noted in the roadmap. Unless a table is identified as global/immutable or append-only, school-owned mutable tables use `id uuid primary key`, required `school_id uuid`, `created_at timestamptz`, `updated_at timestamptz`, and `created_by uuid` where attribution is meaningful. Same-school foreign keys must use composite keys or equivalent trusted validation.

## 9. Target-Domain Integrity, Index, and Migration Rules

- Every join table and tenant-owned child record stores/validates `school_id`; composite foreign keys prevent cross-school references.
- Index foreign keys and the scoped list/history paths used by the screens; add partial unique indexes for one-active-membership rules only after policy approval.
- Use checks for date/range order, status/category values, score bounds, non-negative counts, and positive file sizes. Use trusted functions/triggers only for invariants that ordinary constraints cannot express.
- All Qur'an endpoints reference the same `dataset_id`; endpoint tuples reference actual `ayahs` and are ordered by canonical Surah/Ayah order.
- Assessments, amendments, attendance amendments, points ledger, and audit events are append-only to application roles. Corrections use explicit amendments/reversals.
- Derived progress, leaderboards, and analytics snapshots are rebuildable and never editable sources of truth.
- Keep revisions as assignment/session types, not duplicate tables. Keep score events/ledger as the auditable source; rankings are derived.
- Introduce migrations at the roadmap milestone: 0.1 foundation; 0.2 organization; 0.3 Qur'an/homework/assessment; 0.5 attendance; 0.6 scoring/competition; 0.7 delivery; 0.8 projections; 0.9 sync/offline support.

Names/fields in this target catalog are proposed. Product Owner, Technical Lead, Qur'an Reviewer, and School Representative must approve domain-specific policies, retention, scoring, guardian consent, and the final dataset before the relevant migration is authored.
